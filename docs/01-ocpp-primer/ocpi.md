# OCPI 2.2.1 — how charging networks talk to each other

OCPP connects your server to **chargers**. OCPI connects your server to **other
companies**. Different problem, different protocol, ordinary HTTP.

---

## 1. The problem it solves

Without roaming, every driver needs an account with every network. Ten networks
in your country means ten apps, ten cards, ten monthly statements. That is the
world EV charging is slowly leaving behind.

With roaming, a driver holding **one** card can charge anywhere:

```
  Driver with a Shell card               ┌─────────────────┐
          │                              │  Shell  (eMSP)  │
          │ plugs in at an Ionity site   │  owns the card  │
          ▼                              └────────┬────────┘
  ┌────────────────┐                              │
  │ Ionity charger │                              │ OCPI
  └───────┬────────┘                              │
          │ OCPP                                  │
          ▼                                       ▼
  ┌──────────────────────────────────────────────────────┐
  │              Ionity CPMS  (CPO)                       │
  │                                                       │
  │  "Is this Shell token valid?"   ──── OCPI ───►        │
  │  "43 kWh, €18.40, here is the CDR"  ── OCPI ───►      │
  └──────────────────────────────────────────────────────┘
```

## 2. The two roles

Everything in OCPI depends on which hat you are wearing.

| | **CPO** — Charge Point Operator | **eMSP** — e-Mobility Service Provider |
|---|---|---|
| Owns | The hardware | The customer relationship |
| Publishes | Where the chargers are, what they cost | Which tokens are valid |
| Receives | Commands from partners, token lists | Locations, sessions, CDRs |
| Example | Ionity, Fastned | Shell Recharge, Plugsurfing |

**You are a CPO.** So:

- You **host** Locations, Sessions, CDRs and Tariffs — partners read them from you.
- You **receive** Tokens (their customers' cards) and Commands (their app asking
  you to start a charge).
- A Command from a partner turns directly into an OCPP `RemoteStartTransaction`
  against your own hardware — which is why building OCPI *after* OCPP is easy.
  It is a thin shell over machinery you already have.

## 3. The credentials handshake

This is the part everyone gets wrong. It is a **mutual token exchange**, and
the confusion is that three different tokens are involved.

```
  YOU (CPO)                                           PARTNER (eMSP)
      │                                                     │
      │  ① Out of band — email, a portal — they give        │
      │     you TOKEN_A.                                    │
      │                                                     │
      │  ② GET /ocpi/versions                               │
      │     Authorization: Token <base64(TOKEN_A)>          │
      ├────────────────────────────────────────────────────►│
      │◄────────────────────────────────────────────────────┤
      │     ["2.1.1", "2.2", "2.2.1"]                       │
      │                                                     │
      │  ③ GET /ocpi/2.2.1                                  │
      ├────────────────────────────────────────────────────►│
      │◄────────────────────────────────────────────────────┤
      │     endpoints for locations, cdrs, tokens, …        │
      │                                                     │
      │  ④ POST /ocpi/2.2.1/credentials                     │
      │     Authorization: Token <base64(TOKEN_A)>          │
      │     body: { token: TOKEN_B, url: <your versions> }  │
      │            └── TOKEN_B is generated by YOU.         │
      │                It is what THEY will use to call YOU.│
      ├────────────────────────────────────────────────────►│
      │◄────────────────────────────────────────────────────┤
      │     body: { token: TOKEN_C, … }                     │
      │            └── TOKEN_C is generated by THEM.        │
      │                It is what YOU use to call THEM.     │
      │                                                     │
      │  ⑤ TOKEN_A is now dead. Never used again.           │
```

You end up storing **two tokens per partner, pointing in opposite
directions**:

| Stored as | Generated by | Used by | For |
|---|---|---|---|
| `tokenForUs` | You (TOKEN_B) | Them | Every request they make to you |
| `tokenForThem` | Them (TOKEN_C) | You | Every request you make to them |

Get these backwards and every call fails with `401`, which is exactly what the
broken partner in the dashboard's OCPI screen is demonstrating.

> **Two details that will cost you an hour each.**
>
> The header scheme is the literal word `Token`, not `Bearer`:
> `Authorization: Token <credential>`. And in OCPI 2.2 onward the credential is
> **base64-encoded** before it goes in the header. A surprising number of
> integrations fail on those two lines alone.

## 4. The modules

| Module | As a CPO you… | Carries |
|---|---|---|
| `credentials` | both | The handshake above |
| `versions` | host | Which OCPI versions you speak |
| `locations` | **host** | Your sites, EVSEs and connectors |
| `tariffs` | **host** | Your prices |
| `sessions` | **host** | Charges in progress |
| `cdrs` | **push** | Finished charges, for billing |
| `tokens` | **receive** | Their customers' cards, so you can authorise offline |
| `commands` | **receive** | "Start a charge for my customer at your station" |
| `chargingprofiles` | receive | Smart charging requests from a partner |
| `hubclientinfo` | both | Who is online, when going through a hub |

### Push vs pull

Most modules support both, and the choice is yours:

- **Push** — you `PUT` each object to the partner as it changes. Low latency,
  but you must retry failures and the partner must be up.
- **Pull** — the partner `GET`s a paginated list with a `date_from` filter on
  their own schedule. Simpler for you; staler for them.

In practice: **push CDRs** (money should not wait), **let them pull locations**
(they change rarely), and **cache tokens** they push to you.

## 5. The response envelope

Every OCPI response — success or failure — is wrapped:

```json
{
  "data": [ ... ],
  "status_code": 1000,
  "status_message": "Success",
  "timestamp": "2026-09-13T14:22:03Z"
}
```

**`status_code` is not the HTTP status.** You can get `HTTP 200` with
`status_code: 2001` meaning "invalid parameters". Check both, log both — the
dashboard's OCPI traffic log shows both columns side by side for exactly this
reason.

| Range | Meaning |
|---|---|
| 1000 | Success |
| 2xxx | Client error — your request was wrong |
| 3xxx | Server error — the receiver failed |
| 4xxx | Hub errors |

## 6. What this means for your data model

Here is the pleasant surprise: if you modelled your domain sensibly for OCPP,
OCPI is mostly serialisation.

| Your model | OCPI object |
|---|---|
| `Location` | `Location` — near enough field for field |
| `Station` → `Evse` → `Connector` | `EVSE` → `Connector` (nested inside Location) |
| `Session` | `Session` |
| `Cdr` | `CDR` |
| `Tariff` | `Tariff` — this project's tariff model *is* the OCPI one |

That is not a coincidence. The tariff schema in
[`packages/contracts/src/tariff.ts`](../../packages/contracts/src/tariff.ts) was
deliberately modelled on OCPI's, precisely so that Milestone 12 is a day of
work rather than a redesign. Copying a proven data model is a legitimate
engineering decision, and a good answer when someone asks why your tariffs look
the way they do.

---

## 7. Where OCPI ends

OCPI is not the only roaming protocol. **OCHP** and **eMIP** exist and are used
in parts of Europe; **OICP** (Hubject) is the big commercial hub. OCPI is the
open one, the one most new integrations use, and the one worth learning first.

You will also meet **hubs** — a hub speaks OCPI to everyone and saves you from
doing N bilateral handshakes. The `hubclientinfo` module exists for that.
